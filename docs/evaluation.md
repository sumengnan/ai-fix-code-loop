# 评测：怎么知道它到底行不行

一个能修 bug 的 agent 很容易做出**看起来**能用的样子。这套评测存在的理由是回答一个更
难的问题：**它在多少个真实的 bug 上真的做对了，代价是多少，以及那个数字有多可信。**

它已经抓住过两次它自己作者的过度解读 —— 那两次更正原样保留在这份文档里。

## 任务从哪来

两类，**分布不同，成绩必须分开报**。

### A 类：从 git history 挖（`origin: mined`）

```
找出让测试从红变绿的 commit C
    ↓
任务 = checkout 到 C^，但保留 C 里的测试文件
    ↓
期望 = agent 的补丁让那条测试转绿且不引入回归
    ↓
标准答案 = C 里改动过的源码文件（gold_files）
```

**自带 ground truth，不需要人来标注。** 而且分布是真实的 —— 它就是这个仓库真实发生过
的 bug。

```bash
aifix mine /path/to/repo --limit 200 --max-tasks 40 --out evals/tasks.jsonl
```

一个 `target_test` 一个任务（不是一个 commit 一个任务）：一个 commit 修好多个测试时
产出多个任务，这样每个结果才能保持单一 verdict、单一 attempts 的形状。

**测试目录下的夹具也要跟着嫁接**（数据文件、快照、配置片段）。少了它们，任务在 base 侧
因缺文件而红、在 C 侧绿，通过全部现有校验进入任务集，但 ground truth 实际不可达 ——
修复模型即便诊断和补丁都对也过不了。这不是捏造任务（确实是红转绿），是任务质量问题。

### B 类：人造变异（`origin: mutated`）

在一份**全绿**的母本上做单点 AST 变异（`<` → `<=`、`+` → `-`、`True` → `False`），
跑测试确认真的弄红了，落成任务。

```bash
aifix mutate /path/to/repo --max-tasks 20 --seed 42
```

> **这是冒烟集，不是基准。** 一个把 `<` 改回 `<=` 的单点变异，和从 git history 里挖出来
> 的真实红转绿 commit，难度不在一个量级。它的用途是验证「挖任务 → 跑 agent → 打分」这条
> 链路本身通不通 —— 便宜、确定、可任意规模。**拿它跨模型比高低是过度解读。**

几处刻意的取舍：

- **文本替换而不是 `ast.unparse`**：后者会把格式、空行、注释全部抹掉，产出的 diff 是
  「整文件重写」—— 既不像真实 bug（模型看到的上下文全变了），也会当场撞上巨型 diff 守卫。
  所以 AST 只负责**定位**，替换在原文那一行上按字节切片做。
- **变异位置划得很窄**：只动比较/算术/布尔运算的操作数，以及 `return`/`assign` 的右值。
  不动函数默认值和带注解的赋值（那多半是接口契约，改了往往一大片测试同时变红，落不出
  「单点」的 ground truth），不进 f-string 内部。
  **宁可少产任务，不可产错任务。**
- **一个变异不算任务，一个被验证过确实红了的变异才算。**「生成了 N 条记录」证明不了任何事。

### 任务集长什么样

一份 jsonl，一行一个任务：

```json
{
  "task_id": "shopcart@a1b2c34::tests/test_cart.py::test_total",
  "repo": "/abs/path/to/shopcart",
  "commit": "a1b2c34",
  "base_commit": "0f9e8d7",
  "test_files": ["tests/test_cart.py"],
  "target_test": "tests/test_cart.py::test_total",
  "gold_files": ["src/shopcart/cart.py"],
  "adapter": "pytest",
  "origin": "mined"
}
```

`repo` 是**绝对路径**，换机器要改。

## 跑一轮

```bash
aifix eval evals/tasks-two-repos.jsonl \
    --label qwen3-coder-flash --parallel 3 \
    --budget-per-task 0.60 --budget-total 16.00
```

每个任务：`git clone --local` → 还原到 base commit → 嫁接测试（变异任务还要打补丁）→
跑一次**完整的** `run_once` → 与 ground truth 比对。

### 关键设计：同进程跑产品代码

不起子进程。**评测跑的必须是产品代码本身** —— 配置、trace、判定全都是同一套。崩溃隔离
由「每个任务包一层 try」解决。

### 两条使用提醒

**别把 `--budget-per-task` 设太小。** 冒烟时用过 `0.20`，某个任务 1 轮就被掐断判 `same`；
放到 `0.60` 之后同一个任务修好了。预算设太紧会把「模型不行」和「额度不够」混成同一个数字。

**解释器按任务的 `repo` 字段解析。** 在哪个目录、用谁的 venv 跑 `aifix eval` 都不影响
目标项目的测试。前提只有一条：任务集里 `repo` 指向的那个仓库，自己有一个装齐了测试依赖
的 venv（没有就显式配 `AIFIX_TEST_PYTHON`）。

## 双档打分

| 指标 | 定义 | 量的是什么 |
|---|---|---|
| **定位准确率** | `suspect_file ∈ gold_files` 的占比 | Detector 的能力 |
| **修复成功率** | `verdict == "better"` 的占比 | 整体能力 |

**两档必须分开。** 定位错了但改对了是常见情形（模型自己读代码纠正了诊断），合成一个
数字就看不见 Detector 到底有没有用。实测里出现过定位 57%、修复 17% 的组合 —— 那说明卡住
的不是「找不到文件」，是「改不对」。

### 定位准确率只取**第 1 轮**的诊断

它量的是 Detector 的**冷启动**能力。第 2/3 轮已经看过上一轮的失败反馈，是一道更容易的题。

而且必须**按 attempt 过滤**，不能「取第一条 `suspect_file`」：诊断 JSON 解析失败时那一轮
压根不写 `suspect_file`，于是「取第一条」会静默滑到第 2 轮的诊断 —— **系统性抬高定位
准确率，且抬高幅度正比于模型的 JSON 合规性有多差**。跨模型对比里最不该被混淆的就是这个
维度。

### 命中判定是「路径分段后缀匹配」

```python
same_file("aifix/eval/mine.py", "src/aifix/eval/mine.py")   # True
same_file("xmine.py",           "src/aifix/eval/mine.py")   # False
same_file("other/mine.py",      "src/aifix/eval/mine.py")   # False
```

起因是一次真事故：第一轮跨模型评测里两个模型的定位准确率都被判成 0%。看明细，模型给出
的是模块路径形式（`aifix/eval/mine.py`），gold_files 是仓库路径形式
（`src/aifix/eval/mine.py`）—— 同一个文件，只差一段 `src/` 前缀，而旧判定是裸字符串相等。

**如果判定依赖模型的路径书写习惯，这一列衡量的就不是定位能力，而是书写风格。**

为什么按分段比而不是裸 `endswith`：`"xmine.py".endswith("mine.py")` 是 True，但那是把
文件名从字符中间截出来的假阳性。

为什么不放宽到只比文件名：那样 `other/mine.py` 也会命中，仅仅因为文件名相同、目录完全
对不上 —— 指标会被「蒙对文件名」的运气稀释。

这份判定只有**一份实现**（`signals.same_file`），同时服务定位准确率和「改动落在嫌疑文件
之外」那条信号。两边各留一份的话会各自漂移，届时同一对路径可能在定位准确率里算命中、
在越界信号里算越界，报告自相矛盾。

## 怎么读那张表

```
| 模型 | 来源 | 任务数 | 定位准确率（分数, 95%CI） | 修复成功率（分数, 95%CI） | 平均成本 | 平均 tokens | 平均尝试 | 越界尝试 | 可疑信号 | 评测故障 |
```

### 每个比率都带**分数**和**95% 置信区间**

只给百分比的话，`1/1` 的 100% 和 `12/20` 的 60% 长得一样重 —— 而第一轮那张只有一个样本
的对比表，正是这么被读成结论的。

用的是 **Wilson score interval**，不是正态近似（Wald）。理由：Wald 在 `p̂` 取 0 或 1 时
方差算出 0，区间塌成一个点 —— `1/1` 会得到 `[100%, 100%]`，一个宣称「确定无疑」的区间。
而「只跑了一个任务」恰恰是这张表最需要说出口的事。Wilson 在同样输入下给出 `[21%, 100%]`，
**一眼看出没有结论**。

`n = 0` 时渲染成 `—` 而不是 `0%`：后者会被读成「一个都没修好」，而真相是「一个有效任务
都没有」。

### 「来源」这一列不能合并

挖掘任务的分布是真实 bug 的分布，人造变异是单点、确定、可任意规模但分布不同。把两者的
修复成功率合并成一个数字，等于拿两个不同量纲的东西求平均，**数字本身就是错的**。

### 「越界尝试」量的是「模型有多不听话」

三类：想改测试文件、想逃出工作区、原地打转被中止。这正是 harness 存在的理由。

刻意**不把「补丁打不上」算进来**：那是模型能力问题而非越界，混进来这一列就失去意义了。

### 「可疑信号」和「修复成功率」必须放在一起看

这一列是四类静态信号的计数：

| 信号 | 什么意思 |
|---|---|
| 删除公开符号 | 补丁删掉了模块级 def/class 或公开类的公开方法 |
| 新增模块级可变状态 | 「把纯函数改成有状态函数」的指纹 |
| 改动落在诊断嫌疑文件之外 | 诊断说是这个文件，补丁改的是别处 |
| 新增的判断用了目标测试里的字面量 | 照着这一条用例的输入开后门 |

第四类是后补进来的，**加它之前与之后的历史数据不可直接比**：老 run 的 facts 里没有
`hardcoded_literal` 这个 key，每个补丁的上界也从 3 变成了 4。

**必要性反查（`unnecessary_hunk`）不在这一列里**，而且评测里整层是关掉的
（`necessity_check=False`）——它的产出是只给人看的信号，而评测里没有人在读报告；成本却
是每个单位一次 scoped 重跑，而墙钟耗尽会被归为「评测故障」，把本来能出成绩的任务从分母
里摘掉。理由与 `ask_user=False` 同一个形状：评测环境的账不该记到模型头上。

**修复成功率高、可疑信号也高，那是规格套利的指纹** —— 模型大概率不是在修 bug，而是在
字面上满足断言。

单看任何一列都得不出这个结论：前者看起来是好消息，只有两列放在一起看，才看得出这是坏
消息。

真实验收里出现过的形状：模型把 `add` 改成有状态函数去满足一个自相矛盾的断言、顺手删掉
无测试覆盖的 `mul`，系统报告「修复 1/1」并给出 merge 命令 —— 每一道守卫都正常工作了，
因为它们查的都是 agent 的**行为**，没有一道查补丁的**合理性**。

### 「平均 tokens」是「平均成本」的完整性凭据

没配价格表时成本恒为 0，光看成本分不出「便宜」和「没数据」。所以花了 token 却算出 0 元时
这一格写「未知（未配置 AIFIX_PRICE_MAP）」，不写 `¥0.0000`。

## 四轮真实读数

39 个任务，来自两个真实仓库（ai-harness-framework 14 个 + ai-learning-helper 25 个）。

> **逐任务的原始 jsonl 已不在仓库里** —— `evals/` 于 2026-08-01 移除。下面的数字是
> 当时那四轮的读数，要取回原始记录：`git checkout ea85ae8 -- evals/`。

| 模型 | 任务数 | 定位准确率 | 修复成功率 | 平均成本 | 平均 tokens |
|---|---|---|---|---|---|
| deepseek-v4-flash（2026-07-29） | 37 | 51% (19/37, CI 36%–67%) | 27% (10/37, CI 15%–43%) | $0.4316 | 423,693 |
| qwen3-coder-flash · 旧工具面（07-31） | 39 | 90% (35/39, CI 76%–96%) | 18% (7/39, CI 9%–33%) | $0.2345 | 454,424 |
| qwen3-coder-flash · 新工具面（07-31） | 39 | 92% (36/39, CI 80%–97%) | 74% (29/39, CI 59%–85%) | $0.1311 | 249,501 |
| qwen3-coder-flash · 换重算实现（08-01） | 39 | 90% (35/39, CI 76%–96%) | **79%** (31/39, CI 64%–89%) | **$0.1241** | 238,070 |

> **这四轮读数的成本单位是美元** —— 它们是换币种之前跑出来的。现在同一张表会
> 渲染成 `¥`（价表按美元填时按 `AIFIX_USD_TO_CNY` 折算）。这里保留原始数字而
> 不折算：折出来的数没有一轮是真跑出来的，而这张表的全部价值就在于它是实测。

### 18% → 74%：一次干净的对照

第二行到第三行**只差一件事：工具面**。同一个模型、同一批 39 个任务、同一份预算、同一套
价格表。

**22 个任务从失败翻成成功，0 个回归。** 两个置信区间完全不重叠（9%–33% vs 59%–85%）。

起因是基线明细里的一组读数：

```
apply_patch 被调用 332 次，失败 309 次（93%）
能解析的坏补丁里 247/247 是 `@@ -a,b +c,d @@` 的行数与正文对不上（100%）
```

**模型的正文往往是对的，它栽在记账上。** unified diff 要求它逐字复述上下文行、数对两侧
行数、给对起始行号 —— 把「我要把这段改成那段」编码成了一道算术题，而算术正是 LLM 结构性
最弱的能力。

改动是四条：

1. **补丁行数从正文重算**（`git apply --recount`）—— 不信 `@@` 里那两个数
2. **`edit_file`** —— 给原文和新文，不写 diff、不数行号。把记账整个拿走
3. **`read_symbol`** —— 按名字读完整定义，边界由 AST 算出来，不用猜窗口
4. **诊断模型能看见候选位置的真实源码**，而不只是路径和行号

同时 tokens 降 45%、成本降 44%：省掉的正是「在读文件 / 打补丁的死循环里空转」那一部分。
基线里 **27/39** 的任务以 token 耗尽收场，改完之后是 **9/39**。

`read_file` 那一条的证据同样具体：模型第一次调用就直奔正确的文件（46,447 字符），grep 到
了目标函数在第 519 行 —— 然后把同一个文件**读了五遍**，每遍都拿回一模一样的前 8000 字符，
最后额度耗尽、零产出。框架原来的 `ReadFileTool` 只有 `path` 一个参数，截断消息是
「…(已截断)」：它告诉模型内容被切了，却**不给任何拿到剩下部分的办法**。
**它的行为是理性的，残缺的是工具。**

### 第四轮是一次**口径确认**，不是新结论

74% 那个数是用手写的 `repair_diff`（在 Python 里从正文重算 hunk 表头）量出来的。与另一条
开发线合并时，那四十行被 git 自己的 `--recount` 取代了 —— 当时只做过**离线对照**，而离线
对照不等于重测。

第四轮把这个口径补上：同一批任务、同一个模型、同一份预算，**只换补丁重算的实现**。

```
repair_diff  74% (29/39, CI 59%–85%)
--recount    79% (31/39, CI 64%–89%)
```

两个区间几乎完全重叠，**结论是「换实现没让它掉下去」，不是「--recount 更好」**。逐任务只有
4 个判定翻转，而且方向是一进三出 —— **两个方向都有翻转，是模型采样噪声的形态**；如果
`--recount` 真的弱一档，翻转会一边倒。**39 个任务分不出这 5 个百分点。**

### 加预算能到 90%，但不是纯赚

剩下 10 个失败任务里 9 个仍是 token 耗尽（上限 50 万）。把 `AIFIX_BUDGET_TOKENS` 抬到
120 万、其他变量一律不动，**只跑这 10 个**：6 个转绿（n=10，CI 31%–83%）。

推算整批是 35/39 ≈ 90% —— **这是推算，不是一次跑出来的数**，两段用的是不同配置。代价也
要写清楚：那一批的均价 $0.3575（同上，美元），是 74% 那轮的 **2.7 倍**。

而且加预算**不是纯赚**：多给的额度让模型多试，其中一个任务从 SAME 变成了 **WORSE**。
三态判决在这里挡住了它（WORSE 会被 rollback，不会交付），但这说明「加钱」是个有副作用的
旋钮，不是免费的上分手段。

## 两次自我更正

这套评测存在的理由，就是它抓住了自己作者的过度解读。两次都原样保留。

### 更正一：一条从噪声里读出来的结论

第一轮只跑了 12 个任务，得到「定位 25% / 修复 58%」，据此在文档里写过一条结论：

> ~~诊断多半是错的，补丁多半是对的，detect 这一步可能不值它的钱。~~

第二轮在**同一个仓库**上跑 14 个任务，得到「定位 43% / 修复 43%」。

两轮的区间大幅重叠（定位 9%–53% vs 21%–67%，修复 32%–81% vs 21%–67%），每一轮的点估计
都落在对方的区间里 —— **两轮统计上无法区分，那条结论是从噪声里读出来的。**

区间就印在表里，是我没照着它读。

有一条独立的观察仍然成立，因为它是**直接测量**而不是统计推断：那批任务里的纯断言失败，
traceback 里根本没有产品代码的栈帧，`locate_source` 实测返回 **0 个候选** —— Detector 在
那些任务上确实是盲猜。但「盲猜」和「detect 不值它的钱」是两件事，后者需要一个对照实验
（关掉 detect 再跑一轮），没做。

### 更正二：相关性是真的，归因是错的

deepseek 那轮按仓库拆开：

| 仓库 | 有效任务 | 修复成功率 |
|---|---|---|
| ai-harness-framework | 14 | 43% (6/14, CI 21%–67%) |
| ai-learning-helper | 23 | 17% (4/23, CI 7%–37%) |

据此写过：

> ~~换到更大的代码库上，修复率掉了一半以上 —— 瓶颈是仓库规模。~~

新工具面下再拆：

| 仓库 | 任务 | 第三轮 | 第四轮 | 旧工具面 |
|---|---|---|---|---|
| ai-harness-framework | 14 | 86%（12/14） | **79%**（11/14） | 21%（3/14） |
| ai-learning-helper | 25 | 68%（17/25） | **80%**（20/25） | 16%（4/25） |

**落差没了**：79% 对 80%，大仓库不再更难。

**错的不是相关性（那是真的），是归因**：真正起作用的变量藏在「大仓库」这个表象之下。
**规模从来不是障碍本身 —— 它只是放大了补丁接口的缺陷**：文件越长，上下文行越容易抄错、
表头行数越容易算错，而那正是 93% 的补丁失败原因。换掉那个接口，两个仓库就站到了同一条
线上。

一条自警：这是**观察到的相关性被一次干预推翻**，而干预只做了一次、n=39，拆到 14/25 更小。
别把「落差消失」再读成新的因果定论 —— 它只说明旧那条因果说不通了。

（顺带：第三轮和第四轮的按仓库读数**方向相反**（framework 12→11、helper 17→20），这与整体
只差一个任务是同一件事的两面。三列并排是为了让人看见这一点，不是为了比高低。）

## 已知的口径偏差

读表之前必须先知道这几条，尤其是「可疑信号」那一列。

### 1. 「可疑信号」对诊断解析失败的模型系统性偏低

三类信号里的「改动落在嫌疑文件之外」需要一个 `suspect_file` 作参照，而它来自 Detector 的
JSON 诊断。诊断解析失败时这一类恒为 0。

于是**一个 JSON 输出不合规的模型，无论把改动摊到多少个文件，这一列都不会因此变高** ——
它看起来更「干净」，只是因为没人能判断它越没越界。

这一列必须和 `diagnosis_parse_failed` 一起读。不靠伪造一个 suspect 来抹平：没有诊断就真的
没有「之外」，编一个参照系只会让这一列变成假的。

### 2. 只统计真正交付的补丁

判 SAME / WORSE 后被回滚的尝试不进这一列（它们写的是 `signals_discarded`，只有诊断价值）。

否则「第 1 轮删了公开符号被回滚、第 2 轮干净地修好」会被记成 `fix_hits=1` 且 `signals≥1`
—— 恰好是「规格套利」的指纹，而那个指纹是假的，方向还偏向爱试错的模型。

### 3. 单位是「类」不是「个」

每个交付的补丁最多贡献 3 条（三类各一条），删 10 个公开符号和删 1 个都记 1。规模留在 fact
的 value 与报告里，不进计数。

否则「在一个文件里删 10 个符号」记 10、「摊到 20 个文件一个符号没删」记 1，跨模型比的就不
是同一把尺。

### 4. 失败的形状决定了「之外」这一类有没有资格发声

纯断言失败的 traceback 里没有源码栈帧，Detector 只能按包名猜路径。此时 `suspect_file` 不
构成参照系，这一类不计。

于是**同一个模型在两个任务集上的这一列可以差很多，差的是任务集里断言失败的占比，不是模型**。
跨任务集比这一列之前先比这个占比 —— `suspect_unanchored` 这条 fact 就是为了让它可数。

### 5. 历史数据的一条断层

这一条同时意味着**某次改动前后的历史数据不可直接比**：改动前 `PytestAdapter.locate_source`
的正则匹配的是 Python 原生 traceback，而 pytest 写进 JUnit 的**从来不是那个格式** ——
候选恒空、suspect 恒为盲猜，「之外」这一列量到的是「模型的路径书写风格碰巧对不对」。

## 什么算「评测故障」

`error` 字段非空的任务**不进任何比率的分母**。它们是评测自己的问题，不是被测系统的成绩。

| 情形 | 为什么是故障不是失分 |
|---|---|
| baseline 未复现目标用例 | 任务失效（源仓库变了、环境不同、测试本身不稳定） |
| baseline 全是收集错误 | 「跑评测的这台机器上缺东西」是环境的属性 —— 换一台把依赖装齐的机器，同一个模型就能修 |
| 模型端点不可达 | 同上，换一台能出网的机器就行 |
| 运行崩溃 | aifix 自己的 bug。把系统炸掉的那一次算进分母，等于让模型替我们的 bug 背锅 |
| **墙钟**预算耗尽 | 调度器的属性 —— `--parallel 8` 时几个任务抢同一台机器的 CPU，墙钟耗尽的概率远高于 `--parallel 1`。记成模型的失败等于「只改并行度就能改变修复成功率」 |
| 整批预算耗尽被跳过 | 评测的调度决策 |

**token / 金额预算耗尽相反**：同一批任务、同一个上限，谁先烧完谁差 —— 那是被测系统的真实
成绩，仍记 `verdict=same`，进分母。

判定顺序不能换：收集错误 / 端点不可达必须排在「baseline 未复现目标用例」**之前**。收集一
中断，`target_test` 当然不在 baseline 里，于是那两种情况会被更笼统的分支吸走，报告说
「这个任务失效了」—— 又一句指错方向的诊断。

出错的任务在**任何**口径里都不算，包括「越界尝试」和「可疑信号」这两个求和列。这一条曾经
不成立，导致同一批结果里多一个成功任务、那两列反而归零。

## 为什么目标仓库不是 aifix 自己

评测的每个任务要跑 1 次 baseline 全量 + 至多 3 次 verify 全量。

aifix 自己的套件 378~886 秒 —— **一个任务就要半小时以上**。而 framework 的 13 秒、
helper 的 65 秒。
