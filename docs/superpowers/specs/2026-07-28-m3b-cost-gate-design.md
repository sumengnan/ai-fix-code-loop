# M3b 成本闸 设计规格

日期：2026-07-28
状态：已评审，待实现

---

## 1. 问题

M3 的真实验收跑出两个数字：

- 设 `--budget 0.60`，一次 run 花掉 **$1.60**
- 两个模型各烧 **51~52 万 token 而一个字都没改**（都以 `empty_diff` 收场）

再往下查，还有一个更大的口子：`aifix eval` **根本没有预算参数**，且每个任务各自建预算。默认 `budget_usd = 2.0` 是**每任务**的，所以一个 20 任务的集合跑一轮，上限是 **$40**，没有任何办法给整批设闸。

这三件事是同一个病的三个层面：**预算的检查点都在错误的粒度上**。

| 现状 | 检查点 | 后果 |
|---|---|---|
| 单次 AgentLoop | 只有 token（框架 `BudgetTracker` 不认美元） | 美元闸在最需要的那一层完全不存在 |
| 单 failure | `cli.run_once` 循环顶部 | 单任务评测里那次检查在开跑前就过了，之后不再检查 |
| 整批评测 | 无 | 20 个任务 × $2 = $40，无闸 |

M2 的守卫和预算都是按「挡住坏结果」设计的，**没有一条是按「挡住坏结果的代价」设计的**。空 diff 守卫确实拦住了无效补丁，然后老老实实把重试次数用满；美元预算确实存在，只是检查点在两个 failure 之间，而单任务评测根本没有「之间」。

## 2. 目标与非目标

**做什么**：让「我给这个工具设的花钱上限」成为一句可信的话。

**不做什么**：

- 不做精确到分的硬上限（见 §3 的契约，那是做不到的）
- 不改 `ai-harness-framework`（见 §4 的方案取舍）
- 不做成本预测 / 预估（只做事后累计与熔断）
- 不内置任何模型的价格表（见 §7）

## 3. 契约：越线之后不再发起新的模型调用

**这是本设计最重要的一句话，必须写进 `--help` 与报告。**

成本只有在模型调用返回后才知道。因此任何美元闸的真实语义都是：

> 一旦累计成本越过上限，**不再发起新的模型调用**；已经发出的那一次必然已经花掉。

这与既有 token 闸的语义完全一致——实测 523k vs 上限 500k，超出的正是最后那一步。把它含糊成「硬上限」，就是这个项目反复撞到的那类**静默假安全**：用户以为有保证，系统给不出保证，而差异只在超支之后才暴露。

超支的**上界是可陈述的**：单次 run 内不超过「一次模型调用」的成本；整批评测里，调度器在算出每任务额度的同一把锁内立即把该额度预留进整批已花（任务结束后再回填预留与实际花销的差额），因此某一时刻的「已花」反映的始终是「已发出的最大可能花销」——整批超支只可能来自每个在跑任务自身超出其额度的部分，而单任务的超出量由 `consume()` 的契约兜住（至多一次模型调用）。故整批超支上界 = 并发数 × 一次模型调用的成本（见 §6）。

## 4. 方案取舍

美元闸在单次 run 内部到底在哪里咬合，有三条路：

| 方案 | 精度 | 框架改动 | 取舍 |
|---|---|---|---|
| **一（采用）** 在 `consume()` 里按真实成本熔断 | 事件级，精确 | 无 | 需显式 `aclose()` 异步生成器 |
| 二 把美元换算成 token 上限 | 步级，**严重保守** | 无 | 只能按最贵的输出价估。实测混合费率 ≈ $3.05/M 而输出价 $6/M，会在真实预算的一半处停下 |
| 三 给框架 `BudgetTracker` 加 `max_usd` | 步级，精确 | 有 | 要发版并验证 `ai-learning-helper` 1906 项兼容 |

**采用方案一。**

`agents/runner.py` 的 `consume()` 本来就在逐个消费事件、累加 `ModelUsage.cost_usd`（该值由框架的 `effective_cost` 吃价格表算出）。给它一个上限，越线即停止消费并关闭生成器——精度最高、粒度最细、零框架改动。

**为什么不走方案三**：M1 那两次框架改动是因为**能力缺口**（`LocalSandbox` 需要接管既有目录、`AgentLoop` 需要接收完整初始消息），框架不改就做不到。这次不是能力缺口——aifix 自己完全算得出来。为一道算术去改框架、发版、让另一个项目承担回归风险，不划算。

## 5. 单次 run 内的成本闸

### 5.1 三个咬合点

| 层 | 位置 | 机制 |
|---|---|---|
| 单次 AgentLoop | `agents/runner.py` `consume()` | 事件级累加成本，越线即 `aclose()` 并标记 |
| 单 failure | `budget.py` `RunBudget` | 已有 token 的动态分配，补美元的同样分配 |
| 整个 run | `cli.run_once` 循环顶部 | M2 已有，不动 |

### 5.2 `consume()` 的改动

```python
async def consume(stream, cost_cap: float | None = None) -> AgentOutcome:
    """消费整条事件流；给了 cost_cap 就在越线后停止消费并关闭生成器。"""
```

- 只在 `ModelUsage` 到达后判定（那是成本唯一变化的时刻）
- 越线时置 `AgentOutcome.cost_capped = True`，然后 `await stream.aclose()` 再返回
- **必须显式 `aclose()`**：只 `break` 会把异步生成器留给垃圾回收，其内部 `ExitStack`（框架用它还原纠偏升温）的清理时机就不确定了

### 5.3 为什么不复用 `error` 字段

`AgentOutcome` 新增独立的 `cost_capped: bool`，**不把成本熔断塞进 `error`**。

`detect_node` 用 `outcome.ok`（即 `error is None`）决定要不要解析诊断。把熔断混进 `error` 会让一个**已经拿到手的、可用的**诊断被丢掉——模型可能在被熔断前就已经吐完了 JSON。区分「流被我们主动截断」与「运行出错」，是两件不同的事。

### 5.4 `RunBudget` 的美元分配

`RunBudget` 已有 `for_failure(remaining_failures) -> int` 做 token 的动态分配（全局剩余 ÷ 剩余 failure 数，带下限）。补一个同形状的美元版本，语义与取舍完全一致：动态分配而非固定切分，前面省下的额度自动流给后面难的。

美元的下限（对应 token 的 `FLOOR_TOKENS`）取 `0.0`——与 token 不同，美元额度耗尽时没有「再紧也要给一次有意义尝试」的余地，因为那正是我们要挡住的事。

## 6. 整批评测的总闸

### 6.1 参数

`aifix eval` 新增两个参数，语义必须在 `--help` 里写清楚（当前一个都没有，是最大的口子）：

- `--budget-per-task`：**每个任务**的美元上限
- `--budget-total`：**整批**的美元上限

刻意**不复用 `run` 的 `--budget` 这个名字**：`run` 只有一个 run，不会有歧义；
`eval` 有两级，一个裸 `--budget` 会被读成整批总额。`eval` 今天一个预算参数都
没有，没有向后兼容负担，此刻正是把名字取对的时机。

### 6.2 调度行为

- 每次派发任务**之前**检查整批剩余额度；不足即停止派发
- **已经在跑的任务放它们跑完**——它们的结果是有效数据，中途掐掉等于白花已经花掉的钱
- 每个任务的额度取 `min(单任务上限, 整批剩余)`，并在算出这个额度的**同一把锁内立即预留**进整批已花——读剩余、算额度、预留三步不能跨锁，否则另一个并发槽位会插进来读到预留之前的旧值，超支照原样发生
- 任务结束后回填预留与实际成本的差额（`实际成本 − 预留额度`），异常路径按成本 0 回填、把预留原样退回，避免预留永久占住额度饿死后续任务；被跳过的任务没有预留，不回填

**超支上界**：预留发生在派发前，任一时刻的整批已花反映的是「已经发出的最大可能花销」，后续任务的派发判断能看见在跑任务占用的额度。因此整批超支只可能来自每个在跑任务自身超出其额度的部分，而单任务的超出量由 `consume()` 的契约兜住（至多一次模型调用）——整批超支上界 = 并发数 × 一次模型调用的成本。`--parallel 4` 最坏情况约为 4 次模型调用的成本。这个上界要写进 `--help`。

### 6.3 未运行的任务记成 `error`，不是失败

因整批预算耗尽而没跑的任务，落成 `TaskResult(error="整批预算耗尽，未运行")`。

这**完全复用 M3 已有的区分**：`error` 表示评测自身的问题（不进两个比率的分母，单列在「评测故障」一栏），`verdict` 表示被测系统的成绩。把没跑的任务算成「没修好」会让修复成功率凭空变低——**被测系统替评测的调度决策背锅**，正是 M3 设计 `error` 字段时要挡住的事。

## 7. 无价格表时启动即拒绝

`AifixConfig.price_map` 默认为空。不配价格表，`effective_cost` 恒返回 0，美元闸永远不会触发——**用户设了上限，系统欣然接受，然后一分钱不拦**。

**规则**：用户**明确要求**了美元上限却没有价格表 → 启动时拒绝，给出可操作的报错（说明缺什么、怎么配）。没有明确要求时（用的是默认值）→ 退回 token 闸，不打扰。

**如何判定「明确要求」**：pydantic-settings 的 `model_fields_set` 精确记录了哪些字段是被显式提供的，默认值不在其中。已实测四种来源：

| 来源 | 是否记入 `model_fields_set` |
|---|---|
| 默认值 | 否 |
| 环境变量 `AIFIX_BUDGET_USD` | 是 |
| 构造参数 | 是 |
| `model_copy(update=...)` | 是 |

最后一行意味着 CLI 的 `--budget` **自动被覆盖**——`_cmd_run` 处理该参数走的正是
`model_copy`。所以不需要再单独判 `args.budget is not None`，一处判定管住全部来源。
`eval` 的 `--budget-total` 不进配置对象（见 §9），单独判。

这与 M2 把 `price_map` 的格式错误拦在启动阶段是同一条思路：**成本计算是装饰性的，不该有跑到一半才崩的权力；而成本闸是安全性的，不该有假装生效的权力。**

## 8. 守卫连续触发即放弃

新增 `guard_giveup_limit: int = 2`：**同一条**守卫连续触发达到该次数，即判定这个 failure 没救，直接进入下一个。

**为什么是「同一条」而不是「任意守卫」**：交替触发（空 diff → 巨型 diff）说明模型在换思路，值得再给一次机会；连续两次空 diff 是同一堵墙撞两回。

按当前默认 `fix_guard_retries = 2`（最多三轮），这条规则会砍掉第三轮——正是实测里纯粹浪费的那一轮。

`abort_reason` 记成可区分的值（如 `empty_diff_giveup`），并写一条 `trace.fact`。理由与 M2 给连续失败熔断写的完全一样：**把「钱花完了」变成「出问题了，去看 trace」**——后者信息量大得多，而且省下的额度能流给真有希望的 failure。

## 9. 配置项

| 字段 | 默认 | 说明 |
|---|---|---|
| `budget_usd` | 2.0 | 已有。现在真的会生效 |
| `guard_giveup_limit` | 2 | 新增。同一守卫连续触发多少次即放弃该 failure |

`eval` 的整批上限只走命令行（`--budget-total`），不进 `AifixConfig`——它是**这一次调用**的调度约束，不是项目配置。

## 10. 测试策略

| 目标 | 做法 |
|---|---|
| `consume()` 成本熔断 | 脚本化客户端连续吐带成本的 `ModelUsage`，断言越线后停止消费、`cost_capped` 为真、生成器已关闭 |
| 契约（超支上界） | 断言熔断发生在**越线后的第一次判定**，即最多多花一次模型调用——而不是断言「不超过上限」（那是假的） |
| 熔断不污染诊断 | `detect_node` 在被熔断时仍能解析出已经拿到的诊断（`outcome.ok` 不受影响） |
| 守卫连续放弃 | 脚本化客户端永远只回文本（空 diff），断言只跑了 `guard_giveup_limit` 轮而非 `fix_guard_retries + 1` 轮 |
| 交替守卫不放弃 | 空 diff → 巨型 diff → 空 diff，断言没有提前放弃 |
| 整批总闸 | 造多个任务 + 极小整批额度，断言未跑的落成 `error`、不进分母、出现在「评测故障」列 |
| 无价格表拒绝 | 显式设 `budget_usd` 且 `price_map` 为空 → 启动即报错；用默认值 → 正常跑 |

**特别注意**：本项目已有两次「断言恒真」的教训（表格里 `"0%"` 是 `"100%"` 的子串；`test_violations.py` 九个用例全部自造字符串因而无法发现匹配串来自第三方）。成本相关的断言要比较**具体数值**，不要写 `assert cost > 0` 这类几乎必真的东西。

## 11. 不在本规格内

以下留给后续里程碑，理由见 M3 计划的「交给 M3b 的缺口」表：

- **规格套利**（A 组）：模型改源码以满足不可能的断言。它不是成本问题
- **`MavenAdapter` 与适配层缺陷**（C 组）
- **评测规模化**（D 组）：把对比表从 1 个样本扩到有结论的规模
- **诊断工具**（E 组）：`aifix replay`、SQLite 跨 run 轨迹
